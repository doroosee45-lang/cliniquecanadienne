# Phase 10.2 — Test de charge et vérification de configuration production

**Statut :** Clos
**Origine :** demandé explicitement en clôture de Phase 10.1 : « 10.2 : test de charge sur les endpoints les plus sollicités (dashboard, patients, consultations) + vérification de configuration production (NODE_ENV, JWT_SECRET unique, SMTP hors mode simulation, absence des comptes seed). »

## 1. Test de charge — `tests/loadTestT102.test.js`

Tourne exclusivement contre le serveur isolé (`tests/helpers/isolatedServer.js` — vrai `server.js`, vraie base MongoDB locale jetable), jamais le cluster Atlas partagé ni un serveur de développement laissé allumé, conformément à la contrainte permanente de ne jamais générer de charge/écriture répétée contre l'infrastructure partagée.

**Méthode :** compte médecin de test, jeu de données représentatif (80 patients, 80 consultations), `autocannon` (300 requêtes × 20 connexions par endpoint — calibré pour rester sous le rate-limiter global de développement de `server.js`, 2000 req/15min, qui est un vrai garde-fou de production et non un obstacle à contourner).

**Résultat (exécution locale) :**

| Endpoint | Débit moyen | Latence p50 | Latence p99 | Réponses 2xx |
|---|---|---|---|---|
| Tableau de bord (`/dashboard`) | 300 req/s | 26 ms | 243 ms | 300/300 |
| Patients (`/patients`) | 150 req/s | 78 ms | 105 ms | 300/300 |
| Consultations (`/consultations`) | 150 req/s | 99 ms | 164 ms | 300/300 |

Aucune erreur, aucun timeout, aucune réponse non-2xx sur les 900 requêtes. Ces chiffres sont ceux d'une machine de développement locale (pas d'un environnement de production dimensionné) — la valeur du test n'est pas le chiffre absolu mais l'absence d'erreur/timeout sous charge concurrente et la disponibilité d'une référence si un futur changement dégrade nettement ces temps de réponse.

**Bugs corrigés dans le test lui-même pendant l'écriture (pas dans le code produit) :** le jeu de données de départ utilisait `Patient.insertMany()`, qui n'exécute jamais le hook `pre('save')` générant `numero_dossier` (champ unique) — collision d'index dès le second document. Remplacé par `Patient.create()`. Les consultations de départ omettaient le champ `medecin` (requis par le schéma) — ajouté.

## 2. Vérification de configuration production — `utils/checkProductionConfig.js`

Script CLI + module testable (`checkProductionConfig({env, mongoUri})`), utilisable avant tout déploiement réel : `node utils/checkProductionConfig.js`. Vérifie :

- **`NODE_ENV`** doit valoir `production` (active le rate-limiting strict et désactive les logs `morgan` verbeux, cf. `server.js`).
- **`JWT_SECRET`** doit faire au moins 64 caractères et ne pas contenir l'un des marqueurs de valeur par défaut connus (`.env.example`, ou la valeur actuellement présente dans le `.env` de développement de ce dépôt lui-même).
- **SMTP** (`SMTP_HOST`/`SMTP_USER`) doit être configuré — sinon `utils/mail.js` retombe silencieusement en mode simulé (aucun email réel envoyé : activation de compte, rappel de rendez-vous, réinitialisation de mot de passe).
- **Absence des comptes seed** (`utils/seed.js`) — requiert une URI Mongo, recherche les 28 emails créés par le seed dans la collection `User`.

**Testé** (`tests/productionConfigCheckT102.test.js`, 12/12) : chaque écart pris isolément (NODE_ENV, JWT_SECRET absent/trop court/placeholder, SMTP absent, comptes seed) est bien détecté, pas seulement « le script s'exécute sans planter ». Le contrôle des comptes seed est testé sur une instance MongoDB locale isolée, jamais contre Atlas — celui-ci a réellement servi à `npm run seed` en développement et contient donc légitimement des comptes seed, ce qui fausserait un test dirigé contre lui.

**Exécution réelle contre l'environnement de développement actuel** (informative, pas un défaut à corriger — confirme que le script détecte correctement un état non conforme à la production) :

```
❌ 3 écart(s) détecté(s) : NODE_ENV=development, JWT_SECRET=placeholder connu, 15 comptes seed présents (base Atlas partagée de développement).
```

C'est le résultat attendu pour cet environnement — la preuve que l'outil fonctionne est qu'il détecte correctement ces trois écarts sur la base réelle actuellement utilisée pour le développement, et qu'il détecterait 0 écart sur une configuration de production correctement préparée.
