# T9.8 — Audit des index MongoDB : vérification par `explain()` sous volume représentatif

**Portée :** les 7 gaps prioritaires identifiés par [[T2.4]] (`docs/decisions/T2.4-audit-schemas.md`) : Hospitalization, Consultation, Urgence, Prescription, ImagingResult, Patient.email, AuditLog (requêtes `createdAt` seul).
**Méthode :** T2.4 avait audité le code (déclarations `.index()` par lecture des schémas) sans mesurer d'impact réel. Ici, chaque requête réellement exécutée par les contrôleurs concernés (`hospitalization.controller.js`, `consultations.controller.js`, `dashboard.controller.js`, etc.) a été rejouée avec `.explain('executionStats')`, **avant et après** ajout des index, contre une instance MongoDB locale isolée (pas la base Atlas de dev partagée) peuplée à volume représentatif — pas la base de test réduite (3-8 documents par collection en dev).

## Volume de données seedé (instance locale isolée, détruite après usage)

| Collection | Documents |
|---|---|
| patients | 5 000 |
| hospitalizations | 8 000 |
| consultations | 40 000 |
| urgences | 12 000 |
| prescriptions | 25 000 |
| imagingresults | 15 000 |
| auditlogs | 150 000 |

Distributions de `statut` non uniformes (ex: `en_cours` ~25% des hospitalisations, `sorti` ~58% — proportions plausibles pour un service hospitalier réel), pour que les mesures reflètent une sélectivité réaliste plutôt qu'un cas dégénéré à 50/50.

## Résultats — avant / après

Toutes les requêtes ci-dessous sont les requêtes réelles des contrôleurs (filtres + tri), pas des requêtes synthétiques. `docsExamined` = documents parcourus par le moteur d'exécution (`totalDocsExamined`) ; `stage` = `COLLSCAN` (parcours complet) avant, `FETCH`/`LIMIT` (accès par index) après.

| Requête | Avant (stage, docs examinés) | Après (stage, docs examinés) | Réduction |
|---|---|---|---|
| Hospitalization `{statut:en_cours}` + tri + limite 20 | COLLSCAN, 8 000 | LIMIT, 20 | ÷400 |
| Hospitalization `{date_entree range}` | COLLSCAN, 8 000 | FETCH, 5 | ÷1600 |
| Hospitalization `{patient}` + tri | COLLSCAN, 8 000 | FETCH, 2 | ÷4000 |
| Hospitalization `{medecin_responsable,statut}` | COLLSCAN, 8 000 | FETCH, 58 | ÷138 |
| Consultation `{statut}` + tri + limite 20 | COLLSCAN, 40 000 | LIMIT, 20 | ÷2000 |
| Consultation `{patient}` + tri | COLLSCAN, 40 000 | FETCH, 11 | ÷3636 |
| Consultation `{date_consultation range}` | COLLSCAN, 40 000 (33ms) | FETCH, 54 (0ms) | ÷740 |
| Consultation `{date_consultation range, statut}` | COLLSCAN, 40 000 (32ms) | FETCH, 4 (1ms) | ÷10000 |
| Urgence `{statut}` + tri | COLLSCAN, 12 000 | FETCH, 1021 | ÷12 |
| Prescription `{patient}` | COLLSCAN, 25 000 | FETCH, 6 | ÷4166 |
| ImagingResult `{statut, date_prescription range}` | COLLSCAN, 15 000 | FETCH, 4 | ÷3750 |
| ImagingResult `{date_prescription range}` seul | COLLSCAN, 15 000 | FETCH, 19 | ÷789 |
| Patient `{email}` | COLLSCAN, 5 000 | FETCH, 0 | — |
| AuditLog `{createdAt range}` (graphique 7j) | COLLSCAN, 150 000 (77ms) | FETCH, 1 463 (9ms) | ÷102, 8× plus rapide |

Dans tous les cas, `docsExamined` après correctif est passé de « toute la collection » à « exactement les documents retournés » (`docsExamined == nReturned`, hors les deux requêtes à faible sélectivité — Urgence.statut et Prescription.statut — où le filtre lui-même correspond à une large fraction de la collection ; l'index reste correct, le gain vient surtout du tri déjà satisfait par l'ordre de l'index plutôt que d'un tri en mémoire).

| Modèle | Index | Sert |
|---|---|---|
| `Hospitalization` | `{statut:1, date_entree:-1}` | Liste filtrée par statut + tri par défaut ; `countDocuments({statut})` |
| | `{date_entree:-1}` | Requêtes de plage de dates seules (stats « aujourd'hui ») |
| | `{patient:1, date_entree:-1}` | Historique patient |
| | `{medecin_responsable:1, statut:1}` | Vue « mon service » (dashboard médecin) |
| `Consultation` | `{date_consultation:-1}` | Requêtes de plage de dates seules (dashboard) |
| | `{statut:1, date_consultation:-1}` | Liste filtrée par statut + tri |
| | `{patient:1, date_consultation:-1}` | Historique patient |
| | `{medecin:1, date_consultation:-1}` | Liste par médecin + combos dashboard |

| | `{niveau_triage:1}` | Filtrage par niveau de triage |
| `Prescription` | `{patient:1, date_prescription:-1}` | Historique patient (pharmacie) |
| | `{statut:1, date_prescription:-1}` | Liste filtrée par statut |
| | `{medecin:1}` | Liste par médecin prescripteur |
| `ImagingResult` | `{statut:1, date_prescription:-1}` | Dashboard radiologue (filtré + plage) |
| | `{date_prescription:-1}` | Plage de dates seule (dashboard) |
| | `{patient:1}` | Historique patient |
| | `{priorite:1}` | Filtrage par priorité |
| `Patient` | `{email:1}` (sparse) | Recherche portail, migration [[T2.2]] ; sparse car non requis (cf. T3.1, comptes auto-inscrits sans profil complet) |
| `AuditLog` | `{createdAt:-1}` | Graphiques d'activité 7j/30j — aucun des deux index composés existants ne sert une requête filtrée sur `createdAt` seul |

**Non traité dans ce lot** (gaps « mineurs » de T2.4, faible volume ou faible urgence à ce stade) : Room, DossierChirurgical, Medication, AIPrediction, Bilan/Complication/SuiviPostop, Echographie, RecurringProtocol, Pregnancy, Child, PediatricConsultation — cf. tableau complet dans T2.4 si repris plus tard.

## Vérification de non-régression

- Les 7 modèles modifiés ne changent aucun comportement applicatif (ajout d'index uniquement, aucun champ/validateur/hook touché).
- Suite complète (198/198) rejouée contre la base réelle de dev après construction des nouveaux index par Mongoose (`autoIndex` par défaut, non désactivé dans `config/db.js`) — verte.
- Construction d'index en arrière-plan, non bloquante (MongoDB moderne) — cohérent avec la recommandation déjà actée en T2.4.
- Instance locale de benchmark détruite après usage (`mongo-t98-indexaudit`, port 27119) — jamais connectée à la base Atlas partagée, donc aucun bruit de données synthétiques introduit (cf. [[0009]] pour l'historique de ce risque).
