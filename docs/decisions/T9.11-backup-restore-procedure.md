# T9.11 — Procédure de sauvegarde et restauration MongoDB

**Statut :** Implémenté et testé — restauration réelle vérifiée, pas seulement une exécution sans erreur.

## Contexte et écart par rapport à l'approche standard

L'approche standard (`mongodump`/`mongorestore`, MongoDB Database Tools) n'est pas utilisable telle quelle dans cet environnement : ni `mongodump` ni `mongoexport` ne sont installés sur cette machine, et la base de données (`MONGO_URI`) est hébergée sur MongoDB Atlas (`cluster0.pw00wyy.mongodb.net`), pas en local. Décision validée avec l'utilisateur avant implémentation : écrire un utilitaire de sauvegarde/restauration en JavaScript pur (driver `mongodb` natif + `EJSON` du package `bson`, tous deux déjà présents comme dépendances transitives de Mongoose — aucune nouvelle dépendance ajoutée), plutôt que de dépendre d'un binaire externe absent.

`EJSON` (Extended JSON de MongoDB) est utilisé plutôt que `JSON.stringify`/`JSON.parse` bruts : un `JSON.stringify` classique transformerait silencieusement un `ObjectId` en chaîne de caractères et une valeur `Date` en chaîne ISO, corrompant les types dès la sauvegarde. `EJSON` préserve `ObjectId`, `Date`, `Decimal128`, etc., avec un round-trip exact — vérifié par test (voir plus bas).

## Fichiers

- `backend/utils/backup.js` — `runBackup({ uri, outDir })`. Se connecte à `uri`, énumère toutes les collections (hors `system.*`), écrit un fichier `<collection>.json` (EJSON) par collection dans `outDir`, plus un `_manifest.json` (horodatage, base source, nombre de documents par collection).
- `backend/utils/restore.js` — `runRestore({ uri, inDir })`. Lit `_manifest.json`, puis pour chaque collection listée : vide la collection cible (`deleteMany({})`) avant de réinsérer les documents lus depuis le fichier EJSON correspondant. **Délibérément destructif** — une restauration reproduit exactement l'état sauvegardé, elle ne fusionne pas avec les données déjà présentes dans la cible.

Les deux fichiers sont utilisables comme modules (`require('./utils/backup').runBackup(...)`) ou en ligne de commande :

```bash
node utils/backup.js [--uri=<mongo_uri>] [--out=<dossier>]
# Par défaut : MONGO_URI de .env, dossier backups/<timestamp-ISO>/

node utils/restore.js --dir=<dossier_sauvegarde> [--uri=<mongo_uri>]
# --dir est obligatoire ; --uri par défaut = MONGO_URI de .env
```

## Test de vérification — restauration réelle, pas juste "le script s'exécute"

`backend/tests/backupRestoreT911.test.js` — exigence explicite de l'utilisateur : prouver une restauration réelle, pas seulement l'absence d'erreur au lancement du script.

Méthode : une instance MongoDB **locale isolée** est démarrée pour la durée du test (jamais le cluster Atlas partagé — même principe que l'audit d'index T9.8), sur un port libre choisi dynamiquement et un `dbpath` temporaire propre. Séquence :

1. Démarrage de `mongod` local isolé.
2. Seed d'une base source (`t911_source`) avec des documents couvrant des types variés : `ObjectId`, `Date`, nombres à virgule, tableaux, objets imbriqués — précisément les types qu'un `JSON.stringify` naïf corromprait.
3. `runBackup()` contre la base source → vérifie le manifeste (nombre de documents par collection) et l'existence des fichiers.
4. `runRestore()` vers une base **cible différente** (`t911_target`, même instance) → relecture fraîche des documents restaurés et comparaison avec la source : `_id` reste un vrai `ObjectId` (pas une chaîne), `Date` reste un vrai `Date` avec le même timestamp, tableaux et objets imbriqués identiques, référence `ObjectId` inter-collection préservée.
5. Une seconde restauration consécutive ne duplique pas les documents (vidage avant réinsertion vérifié = idempotence).

6/6 sous-tests verts. L'instance `mongod` de test et ses fichiers temporaires sont proprement arrêtés/supprimés en fin de test (vérifié après exécution : aucun process `mongod` résiduel autre que le service Windows préexistant, sans rapport avec ce test).

## Ce qui reste hors périmètre

- **Planification automatique** (cron quotidien de sauvegarde) : non demandée par T9.11, qui porte sur la procédure et sa vérification, pas sur son exécution récurrente. À envisager séparément si un besoin opérationnel se confirme (sur le même modèle que `utils/appointmentReminders.js`, T8.4).
- **Rotation/rétention des sauvegardes** (purge des anciennes sauvegardes) : non traité, même raison.
- **Chiffrement des fichiers de sauvegarde** : les fichiers EJSON produits contiennent des données patient en clair sur disque — pertinent pour une procédure de sauvegarde en production réelle, mais hors du périmètre strict de cette tâche (documenter/tester la procédure). À signaler si une mise en production est planifiée.
