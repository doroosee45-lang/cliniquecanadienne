# §3.5 — Vérifications complémentaires (Phase 3)

Trois vérifications demandées par le brief Phase 3, indépendantes de T3.1-T3.4 : régression forgot/reset password, cohérence du handshake Socket.IO après les évolutions du modèle `User`, et effectivité du blocage de navigation par `must_change_password`.

## (a) Régression forgot-password / reset-password

**Vérifié par test réel (HTTP, DB réelle) :** `backend/tests/passwordReset.test.js`.

Constats :

- La réponse de `POST /auth/forgot-password` est **identique** (même statut, même message générique) que l'email existe ou non — pas de fuite permettant d'énumérer les comptes (`auth.controller.js:44-47`).
- Le token de reset est un `crypto.randomBytes(32)` hexadécimal, expire après 1h, et est **invalidé après usage** (le rejouer une seconde fois échoue en 400).
- Un token inconnu ou expiré est rejeté en 400.
- Un reset valide permet réellement de se reconnecter avec le nouveau mot de passe ; l'ancien cesse de fonctionner.
- **Constat additionnel (non bloquant, informatif) :** si l'envoi de l'email échoue (`utils/mail.js` via SMTP réel), le contrôleur **révoque silencieusement** le token qu'il venait de poser (`auth.controller.js:56-61`), tout en renvoyant la même réponse de succès générique au client. Comportement volontaire (pas de fuite d'info sur l'échec d'envoi), mais conséquence : si le SMTP est indisponible ou rejette un destinataire, l'utilisateur reçoit un message de succès sans qu'aucun lien fonctionnel n'existe derrière. Pas un régression introduite en Phase 3 — comportement préexistant, mentionné ici car observé pendant le test (nécessite d'utiliser un token simulé directement en DB pour tester la suite du flux, cf. commentaire dans le test).

**Résultat : aucune régression.** Flux intact après les évolutions du modèle `User` (T2.2, T3.4).

## (b) Cohérence du handshake Socket.IO après évolution du modèle `User`

**Vérifié par lecture de code (preuve structurelle, pas seulement une inférence).**

- `server.js` (`io.use(...)`) authentifie chaque connexion socket en lisant le token (cookie, header `Authorization`, ou `auth.token` du handshake), puis `jwt.verify(...)`, et n'extrait que deux champs du payload décodé : `decoded.id` → `socket.userId`, `decoded.role` → `socket.userRole`.
- `User.js::getSignedJWT()` ne signe que `{ id: this._id, role: this.role }` — inchangé depuis l'origine, et **non affecté** par l'ajout de `patient_id` (T2.2), `tentatives_echouees` / `verrouille_jusqu_a` (T3.4), ou `googleId`.

**Résultat : aucune incohérence.** Le handshake Socket.IO est structurellement indépendant du reste du schéma `User` — toute évolution future du modèle qui n'altère pas `_id`/`role` restera sans effet sur l'authentification temps réel.

*(Rappel : ce point est distinct du bug déjà tracké en Phase 9 concernant le token jamais stocké côté client — non traité ici, conformément au périmètre du brief.)*

## (c) `must_change_password` bloque-t-il effectivement la navigation ?

**Réponse : oui pour le portail patient, non pour l'interface professionnelle — et le champ n'est de toute façon jamais positionné pour un compte staff.**

- **Portail patient (`Portal.jsx`) :** blocage réel et non contournable. Le flag vient de `GET /portal/me` (`portal.controller.js:33`), pilote une modale (`modalChangePwd`) qui s'ouvre automatiquement et **ne peut pas être fermée** tant que `must_change_password` est vrai (bouton Annuler masqué, `onClose` conditionné).
- **Interface professionnelle (staff) :** aucune occurrence de `must_change_password` dans `App.jsx` ni dans aucun layout staff — **aucun mécanisme de blocage n'existe**, même si le flag était positionné.
- Or il ne l'est jamais pour les comptes staff : ni `hr.controller.js::create` (mot de passe généré aléatoirement, jamais communiqué nulle part), ni `settings.controller.js::createUser` (mot de passe fourni tel quel par le formulaire admin) ne définissent `must_change_password: true`.

**Résultat : gap réel, documenté séparément dans [ticket 0003](../tickets/0003-must-change-password-non-applique-comptes-staff.md)** (hors périmètre T3.1-T3.4, non corrigé ici conformément au brief qui demande de documenter les constats hors périmètre plutôt que de les résoudre).
